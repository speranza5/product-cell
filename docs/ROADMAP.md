# Roadmap de construcción

Este roadmap construye el sistema de trabajo. Cada tracker conservará su propio roadmap de producto. Una etapa termina por evidencia, no por cantidad de documentos escritos.

| Etapa | Resultado | Condición de salida |
|---|---|---|
| E00 | Base documental y continuidad | Repo independiente, guías y estado comprobados |
| E01 | Contexto del piloto consolidado | Producto elegido, reglas con fuentes y contradicciones resueltas o registradas |
| E02 | Flujo y arneses configurados | Agentes y skill detectados; entradas y salidas verificadas en prueba en seco |
| E03 | Primer circuito económico funcionando | Un tweak y un bugfix reales aceptados, con learning y métricas |
| E04 | Refinamiento y etapa de roadmap | Una historia pasa PM → Tech Lead → Dev → Reviewer y entrega, con evidencia |
| E05 | Entrega y operación reproducibles | Runbook, rollback y checks pertinentes probados en entorno adecuado |
| E06 | Biblioteca de conocimiento útil | Corpus curado y búsquedas textuales evaluadas con preguntas reales |
| E07 | RAG evaluado si se justifica | Decisión de adoptar o postergar basada en comparación con búsqueda textual |
| E08 | Método portable | Segundo tracker adopta el método sin copiar restricciones ajenas |

## Política de cambios

Se puede dividir, reordenar o postergar una etapa con motivo y decisión registrada. E07 puede terminar con “postergar RAG”; no obliga a implementarlo. No inventar fechas de entrega antes de conocer el piloto. Requisitos operativos relevantes deben entrar al refinamiento aunque su automatización completa ocurra en E05.
